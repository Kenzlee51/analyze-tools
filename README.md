# analyze-tools

Набор скриптов для анализа избыточности исходных текстов и происхождения
файлов дистрибутива.

Задача, которую решает инструмент: убедиться, что переданный заказчиком
носитель исходных текстов (обычно диск 12) содержит **только** файлы,
относящиеся к данному изделию, и что файлы дистрибутива (диск 91)
действительно получены из этих исходных текстов. Нарезка нескольких
дистрибутивов разного наполнения из одного исходного носителя не
допускается.

## Структура каталогов

```
analyze-tools/
├── scripts/
│   ├── unpack.sh           рекурсивная распаковка архивов
│   ├── generate_json.sh    снятие хешей, формирование src.json / bin.json
│   └── analyze-json.py     анализ (5 проходов)
├── lib/
│   └── utilities.yaml      реестр компиляторов, линковщиков, интерпретаторов
├── test/
│   ├── <файл>.js           контрольный файл самотеста хеширования
│   └── <файл>.txt          эталонный хеш
├── src/                    ВХОД: сюда кладутся носители
│   ├── <ИЗДЕЛИЕ>/{src,bin}
│   ├── TRUSTED.GENERAL/{src,bin}
│   └── TRUSTED.<ИЗДЕЛИЕ>/{src,bin}
├── unpacked/               распакованное дерево (создаёт unpack.sh)
├── buildography/builds/
│   └── <ИЗДЕЛИЕ>/*.json    трасса сборки
├── results/
│   └── <ИЗДЕЛИЕ>/
│       ├── sources/        <ИЗДЕЛИЕ>_src.json, <ИЗДЕЛИЕ>_bin.json
│       └── izb/
│           ├── try{N}/     полные результаты прогона
│           └── summary{N}/ только непустые отчёты + README.txt
└── logs/
```

## Алгоритм хеширования

Хеш — **ГОСТ**, считается командой из `HASH_CMD` в `generate_json.sh`:

```bash
HASH_CMD="rhash -G"
```

Это критически важно помнить при любой ручной сверке. `sha256sum` даёт для
того же файла совершенно другое значение, а длина строки у обоих 64
шестнадцатеричных символа, поэтому на вид результаты неотличимы. Сверка
хеша из отчёта с результатом `sha256sum` приводит к ложному выводу о
подмене файла.

Перед каждым прогоном `generate_json.sh` выполняет самотест: снимает хеш с
`test/*.js` и сравнивает с эталоном из `test/*.txt`. **Любая ручная проверка
должна делаться той утилитой, которая воспроизводит этот эталон.**

На сборочных машинах, где нет `rhash`, эквивалент даёт `gostsum` (проверено
совпадением с файлами `*.gostsum`, которыми подписываются образы). Перед
использованием убедитесь на контрольном файле.

## Порядок запуска

```bash
# 1. Распаковка
./scripts/unpack.sh                             # все носители
./scripts/unpack.sh --single-project NPUR.34018-01

# 2. Снятие хешей
./scripts/generate_json.sh -t 6
./scripts/generate_json.sh --single-project TRUSTED.GENERAL

# 3. Анализ
./scripts/analyze-json.py
./scripts/analyze-json.py --project NPUR.34018-01
```

### Повторный прогон генератора НЕ обновляет json

`generate_json.sh` не перезаписывает существующий файл. При повторном
запуске он создаёт `<имя>_v1.json`, `_v2.json` и так далее, сообщая об этом
единственной строкой `[WARN] File exists, writing to: ...`. Анализатор при
этом продолжает читать исходный файл.

Поэтому **перед повторной генерацией каталог `results/<ИЗДЕЛИЕ>/sources/`
нужно чистить вручную.** Иначе прогон молча пройдёт по устаревшим данным, и
внешне всё будет выглядеть убедительно: свежие даты каталогов, полный вывод,
нулевой код возврата.

Проверка накопившихся версий:

```bash
find results -name '*_v[0-9]*.json' -printf '%TY-%Tm-%Td %TH:%TM  %p\n' | sort
```

## Согласованные (доверенные) носители

Часть изделия законно состоит из сторонних материалов, состав которых
согласован отдельно — например СВВП (кэши репозиториев, библиотеки). Такие
материалы проверяются точно так же, как исходники изделия, поэтому они
кладутся в `src/` как обычные носители, с плоским именем:

```
src/TRUSTED.GENERAL/{src,bin}          действует для ВСЕХ изделий
src/TRUSTED.<ИЗДЕЛИЕ>/{src,bin}        действует только для этого изделия
```

`GENERAL` подхватывается всеми изделиями, которые анализирует
`analyze-json.py`. Всё, что специфично для изделия, кладётся в его
собственный каталог, даже если изделие пока одно: `GENERAL` действует
широко, и его стоит держать только для действительно общего — ТПО, штатных
пакетов ОС.

Инвентаризация делается тем же `generate_json.sh`, после чего
`analyze-json.py` подхватывает `results/TRUSTED.*/sources/*.json`
автоматически.

### Почему плоское имя, а не вложенность

Напрашивается `src/TRUSTED/GENERAL/{src,bin}`, но это не работает.
`unpack.sh` и `generate_json.sh` строго двухуровневые: оба обходят `src/*/`
(соответственно `unpacked/*/`) и ищут внутри ровно `src` и `bin`.

При вложенности `generate_json.sh` увидел бы проект `TRUSTED`, не нашёл бы у
него ни `src`, ни `bin`, напечатал бы `[INFO] Subdir not found, skipping`
дважды и **вышел с кодом 0, не создав ни одного json**. Ни ошибки, ни
предупреждения. При плоском имени оба скрипта работают без правок.

### Проверка имён каталогов

Имя проверяется строго и регистрозависимо. Каталог, совпадающий с ожидаемым
без учёта регистра, но не совпадающий точно (`trusted.general` вместо
`TRUSTED.GENERAL`), считается **ошибкой**: печатается предупреждение и, при
интерактивном запуске, задаётся вопрос о продолжении.

```
[WARNING] Каталоги согласованных носителей с неверным именем:
  найдено : trusted.general
  ожидается: TRUSTED.GENERAL   (регистр имени)
Такие каталоги НЕ будут использованы как доверенные.
Всё их содержимое попадёт в 'происхождение не установлено'.

Продолжить без этих носителей? [y/N]:
```

Так сделано намеренно. Молча проигнорированный доверенный носитель приводит
к тому, что весь его состав уезжает в «происхождение не установлено», а
причина этого из отчёта неочевидна. Каталоги `TRUSTED.*`, относящиеся к
**другим** изделиям, игнорируются молча — это нормальная ситуация.

### Масштаб носителя и расход памяти

Согласованный носитель может быть очень большим. СВВП 0.9.6 после
распаковки — **2.23 млн файлов и 62 ГБ**, что даёт `TRUSTED.GENERAL_src.json`
размером порядка **1.3–2 ГБ**.

Поэтому инвентаризация читается **потоково** и никогда не материализуется
целиком: обычный `json.load` развернул бы такой файл в список из 2.23 млн
словарей по пять ключей — пять-восемь гигабайт объектов Python на пике, то
есть гарантированный OOM, причём ещё до построения индекса.

Индекс (`TrustedIndex`) устроен под этот объём:

- ключ хранится **целым числом**, а не 64-символьной строкой (строка весит
  около 113 байт, целое примерно 32);
- значением хранится не полный путь, а **контейнер** — ближайший архив, то
  есть ровно то, что фигурирует в отчёте. Контейнеров на носителе тысячи, а
  не миллионы, поэтому при интернировании все пути схлопываются в несколько
  тысяч строковых объектов.

Замер на 2.23 млн записей: **368 МБ, 167 байт на запись**, разбор около
20 секунд.

Точный путь файла внутри носителя при этом не хранится. Если он понадобится
для разбора единичного случая, он находится по хешу:

```bash
grep -B2 '"hash": "<хеш>"' results/TRUSTED.GENERAL/sources/TRUSTED.GENERAL_src.json
```

Если формат, который пишет `generate_json.sh`, изменится, потоковый разбор
не найдёт ни одной записи — тогда выполняется откат на `json.load` с громким
предупреждением в лог. Это сделано намеренно: расхождение форматов должно
быть видно явно, а не проявляться нехваткой памяти.

### Сверка идёт по хешу, а не по пути

Принципиальный момент. Путь говорит «откуда взяли», хеш — «что именно
взяли». Только второе отличает согласованный носитель от постороннего кэша,
поднятого по тому же адресу.

Пример из практики: сборка тянет пакеты через
`pip3 download --index http://localhost:9000`, где по адресу слушает
`python3 -m http.server`, отдающий `/opt/centrem/svvp/pypi-cache`. Списание
по пути `/opt/centrem/svvp/` объявило бы доверенным всё, что пришло с этого
адреса, не проверив содержимое. Сверка по хешу проверяет именно содержимое.

## Проходы анализа

| Проход | Что делает |
|---|---|
| 1 | Принадлежность по хешу: direct / parent / redundant-by-hash |
| 2 | Обратный обход от дистрибутива: compiled_not_copied_to_distr |
| 3 | Интерпретируемые файлы: executed / compiled_used / compiled_unused / copied / not_used |
| 4 | Происхождение файлов дистрибутива |
| 5 | Разбивка по дискам (`--by-disk`) |

### Проход 4: происхождение

Категории от «чистых» к «подозрительным»:

| Категория | Значение |
|---|---|
| `compiled_from_src` | Появился в ходе сборки, происхождение до источника не прослежено |
| `binaries_from_src` | Хеш есть в src.json — готовый бинарь лежал в исходниках |
| `untraced_from_src` | Хеш в src.json, трассировщик не видит попадания в дистрибутив |
| `external_built` | Собран, но зависимости не из src.json |
| `external_prebuilt` | Пришёл готовым, трассировщик видит как зависимость |
| `untraced_external` | Ни в src.json, ни в трассе |
| `external_package_content` | Файл внутри внешнего пакета, источник известен трассе |
| `system_binaries` | Системный путь внутри дистрибутива |

#### Чего `compiled_from_src` НЕ означает

Это **else-ветка**. Файл попадает в неё при трёх условиях: его хеш является
выходом прослеженной команды; среди переживших фильтрацию зависимостей нет
подозрительных внешних; хеша нет в `src.json`. Участие исходного текста
изделия не проверяется ни на одном шаге, поэтому название категории
утверждает больше, чем код измеряет.

Условие «подозрительных зависимостей не осталось» выполняется слишком легко:
у типичной команды в трассе 280–320 зависимостей, и подавляющая их часть —
чтения динамического загрузчика (`libc`, `locale-archive`,
`gconv-modules.cache`, `libz`), которые целиком уходят в системный фильтр.
Проверять оказывается нечего.

Измерение на NPUR.34018-01 — 346 записей, 124 уникальных файла:

| Производящая операция | Файлов |
|---|---|
| `wheel pack` (переупаковка чужого колеса) | 53 |
| `python -m build` (сборка чужого пакета) | 27 |
| `bsign` (ГОСТ-подпись готового ELF) | 22 |
| `unzip` (побайтовая распаковка) | 6 |
| `pip install` | 5 |
| `dpkg` | 4 |
| `node` | 4 |
| `tar` | 2 |
| `pip download` | 1 |

Ни одного компилятора. То есть ни один из этих файлов не собран из исходных
текстов изделия, хотя все они так помечены.

#### Разбор по происхождению: две оси

Поэтому рядом с категорией строится разбор по **терминалу цепочки** — по
тому файлу, из содержимого которого данный в конечном счёте получен.

**Ось 1, происхождение** (она же категория отчёта):

| origin | Значение |
|---|---|
| `product_src` | Терминал в `src.json` изделия |
| `approved_source` | Терминал на согласованном носителе, совпадение по хешу |
| `download` | Терминал на сетевой загрузке, адрес указан |
| `unresolved` | Терминал не опознан — происхождение не подтверждено |

Порядок проверки: `src.json` → `TRUSTED` → загрузка → не установлено.
Поскольку `TRUSTED` проверяется раньше загрузки, в `download` остаётся
только то, что скачано **и** не найдено ни на одном согласованном носителе.
Это мягкое, но настоящее замечание: источник вне переданного комплекта.

**Ось 2, операция** (атрибут записи, не категория):

| operation | Создаёт содержимое? |
|---|---|
| `compiled` | да — компилятор, ассемблер, линковщик |
| `built` | да — `setup.py`, `python -m build`, `pip install`, node |
| `repacked` | нет — `wheel pack`, `dpkg-deb -b`, `tar -c` |
| `signed` | нет — `bsign`, `gpg --sign` |
| `extracted` | нет — `unzip`, `tar -x`, `dpkg --unpack` |
| `copied` | нет — `cp`, `install`, `mv` |
| `transformed` | нет — `strip`, `objcopy`, `patchelf` |
| `downloaded` | терминал — `pip download`, `wget`, `curl` |

Для операций, которые содержимое не создают, происхождение ищется во входе
команды. `strip` и `bsign` попадают в один класс по одной причине: они
меняют байты готового файла, из-за чего его хеш не совпадает ни с одним
исходником и файл выглядит «новым», хотя содержательно это тот же сторонний
бинарь.

Пример разобранной цепочки:

```
origin=approved_source  op=repacked
  TRUSTED.GENERAL/src: pypi-cache/Django/Django-2.2.16.tar.gz
  chain: repacked(wheel pack)
```

Отчёты: `try{N}/pass4/{project}_origin_product_src`,
`_origin_approved_source`, `_origin_download`, `_origin_unresolved`.
В `summary{N}/` выносится только `compiled_from_src` единым списком —
сущности в сводке не множатся.

#### Опознание операции идёт не по argv[0]

В реальной трассе настоящий инструмент часто стоит не первым:

```
/usr/bin/python3 /usr/bin/pip3 download --index http://localhost:9000 ...
xargs -i wheel pack {}
/usr/bin/python3 -c "import sys, setuptools, tokenize; ... 'setup.py' ..."
/usr/bin/python3 .../pep517/_in_process.py prepare_metadata_for_build_wheel
```

В первых двух случаях `argv[0]` — это `python3` и `xargs`, то есть
интерпретатор и обвязка. В третьем имя собираемого пакета и путь к
`setup.py` находятся **внутри строки после `-c`** и ни одним отдельным
элементом argv не представлены.

Поэтому опознание идёт по двум каналам: цепочка первых неопционных токенов и
текстовый поиск ключевых слов по всей команде. Именно из-за разбора только
по `argv[0]` весь питоновский конвейер изделия выглядел для анализатора
безликим, и 346 файлов уходили в else-ветку.

## Фильтрация по путям

Два разных списка, которые нельзя путать.

**`SYSTEM_PATH_PREFIXES`** — пути на **хосте сборки**. Расширять можно.
Содержит системные библиотеки, заголовки, данные, а также каталоги
исполняемых файлов хоста (`/usr/bin/`, `/bin/`, `/sbin/`, `/usr/sbin/`,
`/usr/local/bin/`, `/usr/local/sbin/`, `/usr/doc/`) и тулчейн ТПО
(`/opt/centrem/tpo/`).

Обоснование для каталогов исполняемых файлов: это инструментарий хоста, его
никто не передаёт как носитель, сверять по хешу не с чем, и компилятор
физически не может быть источником **содержимого** файла дистрибутива — он
его производит, но не является его материалом. Проверено на трассе
NPUR.34018-01: все 235 выходов в этих каталогах — файлы `*.dpkg-new`,
которые создаёт `dpkg` при установке пакетов сборочной машины; ни одного
файла изделия.

Намеренно указан `/opt/centrem/tpo/`, а **не** `/opt/centrem/` целиком: в
`/opt/centrem/svvp` лежит СВВП, у которого есть инвентаризация, и он должен
проверяться по хешу через `TRUSTED`.

**`DISTRIB_SYSTEM_PREFIXES`** (внутри `analyze_pass4`) — пути **внутри
дистрибутива**. Расширять нельзя. Добавление сюда `usr/bin/` привело бы к
тому, что собственные бинари изделия стали бы считаться системными.

Каждая отфильтрованная по пути зависимость получает `reason` в
`filtered_deps`: `header`, `build_host_executable`,
`build_host_toolchain_tpo`, `system_path`. Фильтр по пути всегда грубее
фильтра по хешу, поэтому он обязан быть видимым в отчёте.

## Известные ограничения

**Обрыв обратной цепочки.** Расширение фронтира в Pass 4 ограничено тремя
итерациями, а `_scan_pass` выбрасывает **путь** зависимости, если её хеш
является чьим-то выходом (считает промежуточным артефактом) — так молча
проглатываются внешние архивы. Сейчас это компенсируется снаружи разбором
по происхождению, но к самой проблеме нужно вернуться: требуется решение
более изящное, чем увеличение лимита итераций.

**Разбор `other` в `utilities.yaml` не загружается.** `load_utilities_lists`
читает только `compilers`, `linkers` и `interpreters`. Раздел `other`
служит реестром встреченных утилит и документацией; правила опознания
операций заданы в коде, в `detect_operation`.

**Глубина разбора происхождения** — 3 раунда, каждый раунд это один проход
по трассе. Переопределяется переменной окружения `ORIGIN_ROUNDS`.

## Замечания к буйлдографии

Накопленные по ходу работы, для передачи владельцам трассировщика.

**Алгоритм хеширования не назван.** Поле зовётся просто `hash`, и по его
содержимому невозможно понять, ГОСТ это или SHA-256 — у обоих 64
шестнадцатеричных символа. Одна строка в шапке с именем алгоритма снимает
целый класс ложных выводов о подмене файлов.

**События переименования обнаруживаются, но не сохраняются в JSON.**
`clang -cc1` пишет объектный файл в случайный временный путь и затем
переименовывает; в трассе остаётся временный путь. Содержимое при этом не
меняется, поэтому сопоставление по хешу выручает, но путь теряется.

**Трассируется только дерево процессов сборки.** Обращения к локальным
серверам пакетов (`pypi-server` на `:9000`, verdaccio, satis) не
прослеживаются: видно, что `pip download` получил файл с таким-то хешем, но
не видно, что сервер его отдал. Цепочка обрывается на сетевой границе и
